# v0.3.5

Close a notebook's allocation attempt when an HTTP 503 is received before any runtime endpoint is captured, so the same notebook can be reopened with a new idempotency key. Keep the failed request and the unconfirmed provider release in the diagnostic ledger. Count failed attempts separately from confirmed and unresolved runtimes. Reconcile existing matching records during notebook reads, compute status checks, opens and maintenance. Preserve same-key idempotency and concurrent-open protection.

Apply migration `0013_glorious_the_hand.sql` through the existing Sites deployment workflow. It adds the `allocation_failed` ledger flag and updates the per-notebook unique index so a failed allocation no longer occupies the opening slot. Existing records are retained. Preserve the Site identity, origin, secrets, data and audience.

Each open call still submits one allocation attempt. This release does not add an automatic retry loop or guarantee provider capacity. Reusing the same key returns the original attempt; use a fresh key to start again.

Validation covers automated tests, type checking and production builds. It does not establish fresh Google OAuth or a live Colab allocation.
